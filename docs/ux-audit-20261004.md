# UX-аудит «заявка — задание — выезд», 04.10.2026

## Вывод и границы

Структура из трёх сущностей соответствует работе сервиса, но интерфейс ещё не объясняет её последовательно. Главные препятствия — потеря контекста при переходах, смешение факта и переноса остатка, непонятные ограничения стадий, две точки редактирования состава работ и разные назначения людей в заявке, задании и выезде. Визуальный редизайн до устранения этих проблем будет преждевременным.

База проверки: main ad2921c, текущие исходники, DOM-тесты, production read-only запросы. Актуальная контрольная точка находится в docs/entity-responsibility.md и docs/entity-responsibility-release.md; старый CONTINUE начинался с 29 сентября. Production подтвердил migration 20261004180339 entity_responsibility, 17 активных заявок (9 open, 8 done), 18 канонических заданий — все draft. Это историческое состояние, а не повод автоматически присвоить факт или сменить стадии.

GitHub: подтверждены чтение и push permission. Supabase: оба проекта доступны через MCP. Production данные и схема этим этапом не менялись. На QA установлена independent_request_task_stages (ledger 20261004191431); синтетические проверки откатились.

После сообщения пользователя «вошел» подтверждён вход admin. На production выполнен desktop-проход диспетчера (заявки, задания, выезды), заявки с дочерним заданием №33, карточки задания и общего выезда двух заявок: план/факт, экономика и раскрытая проверка присутствия. Использованы DOM и реальные скриншоты; записи не сохранялись. Это экспертный UX-аудит, **не usability-тест с пользователями**. Исправленный PR ещё не опубликован: его desktop/mobile предпросмотр блокируется browser credential protection. Узкий экран 390 px и отдельные браузерные сессии инженера/куратора не подтверждены.

UX Pilot доступен. list_pages вернул 0 страниц. preview_flowchart использован для черновой схемы процесса; аудита реальных экранов через preview_ux_review не было. Сгенерированный граф включал автоматическое обновление заявки после дочерних подтверждений — этот пункт отклонён как противоречащий проектной модели. Граф не является доказательством правильности бизнес-правил.

## Последовательность UX-работ до UI

1. Единое правило стадий: сначала подготовить заявку, затем запускать задание. Выпустить уже проверенную QA-миграцию вместе с клиентом.
2. Один понятный маршрут планирования: заявка задаёт коммерческий состав; задание определяет порученный объём, людей, период и результат. Доработать сценарий дополнительной работы и корректировки цены с аудитом, не просто разблокировать исторические поля.
3. В задании дать два явных действия для выезда: создать новый / добавить в существующий. В выборе показывать дату, авто, команду, клиентов и уже включённые задания.
4. Перестроить порядок блоков по задаче роли. Финансовые настройки и делегирование не должны отодвигать ежедневное выполнение. Независимые назначения объяснять на месте, без автоматического копирования исторического факта.
5. Сделать архив и сверку выездов доступными: явные статусы проверки присутствия/затрат, переход к нерешённому пункту, доступные карточки при фильтрации.
6. Пройти QA-сценарии всех ролей на desktop/390 px с ошибкой сохранения, частичным результатом, переносом и общим выездом. Только после этого заниматься цветами, типографикой и декоративными деталями.

Критерий готовности UX: диспетчер может найти нужную сущность, увидеть следующий шаг и причину ограничения; инженер записать факт без чтения административных блоков; куратор отличить окончание дороги, проверку присутствия и принятие работы. Переходы сохраняют исходный контекст, несохранённые правки защищены, сервер соблюдает то же правило, что показывает экран.

## Проверенные и обязательные пользовательские потоки

1. Диспетчер: заявка → список имеющихся заданий → редактирование нужного задания либо создание дополнительного → сохранение состава/команды/периода → назначение.
2. Выездная работа: задание → новый или существующий общий выезд → выбор нескольких заданий → сохранение маршрута/команды → исполнение и проверка присутствия. Результат работ и материалов вводится в задании.
3. Депо/удалённая работа: назначение и результат задания без обязательного выезда.
4. Частичное выполнение: сохранить сделанное → перенести только остаток с причиной → новое задание; исходный факт и цены остаются в источнике.
5. Куратор: проверить результат → при остатке/активных выездах увидеть причину блокировки → подтвердить после устранения условий. Подтверждение поездки и работ — разные действия.
6. Переходы между карточками: сохранить/отказаться от ухода/явно сбросить правки → вернуться к исходному ID и фильтрам.
7. Владелец после делегирования: вмешательство с причиной и история, уведомление текущему куратору.
8. Историческая заявка: не трактовать закрытый статус как факт выполнения; при известном факте использовать отдельное основание.

Первые DOM-регрессии добавлены для прогресса, фильтров/исходных ссылок, защиты переходов, сохранения disabled-состояний, доступности переноса и блокировки закрытия при активном общем выезде. Эти проверки не заменяют проход пунктов 1–8 в живом браузере.

Для финальной проверки нужны диспетчер/инженер/куратор, desktop и узкий экран 390 px, одна заявка с двумя заданиями, один общий выезд с заданиями двух заявок, частичный результат/материал, перенос, отмена, офлайн и повторный вход. Производственные записи использовать только для чтения; действия выполнения — на синтетических QA-данных.
