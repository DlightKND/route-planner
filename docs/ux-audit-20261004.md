# UX-аудит «заявка — задание — выезд», 04.10.2026

## Вывод и границы

Структура из трёх сущностей соответствует работе сервиса, но интерфейс ещё не объясняет её последовательно. Главные препятствия — потеря контекста при переходах, смешение факта и переноса остатка, непонятные ограничения стадий, две точки редактирования состава работ и разные назначения людей в заявке, задании и выезде. Визуальный редизайн до устранения этих проблем будет преждевременным.

База проверки: main ad2921c, текущие исходники, DOM-тесты, production read-only запросы. Актуальная контрольная точка находится в docs/entity-responsibility.md и docs/entity-responsibility-release.md; старый CONTINUE начинался с 29 сентября. Production подтвердил migration 20261004180339 entity_responsibility, 17 активных заявок (9 open, 8 done), 18 канонических заданий — все draft. Это историческое состояние, а не повод автоматически присвоить факт или сменить стадии.

GitHub: подтверждены чтение и push permission. Supabase: оба проекта доступны через MCP. Production данные и схема этим этапом не менялись.

Облачный браузер открыл рабочий сайт, но после защищённого входа показал Failed to fetch. Положительного сигнала авторизации нет. Дополнительный автономный предпросмотр не удалось осмотреть из-за ограничения browser credential protection. Поэтому это аудит реализации и поведения DOM, **не законченный визуальный или пользовательский usability-тест**. Положение элементов, реальная длина карточек, видимость на узком экране и поведение живых ролей требуют повторного браузерного прохода.

UX Pilot доступен. list_pages вернул 0 страниц. preview_flowchart использован для черновой схемы процесса; аудита реальных экранов через preview_ux_review не было. Сгенерированный граф включал автоматическое обновление заявки после дочерних подтверждений — этот пункт отклонён как противоречащий проектной модели. Граф не является доказательством правильности бизнес-правил.

Кнопки стадий учитывают только доступные клиенту данные. Проверка сервера остаётся обязательной: скрытый выезд, параллельная правка или изменение прав могут дать дополнительный отказ.

## Оставшиеся вопросы до UI

| Приоритет | Сценарий | Наблюдение и следующий шаг |
|---|---|---|
| P1 | Независимые стадии | Живой production order_transition автоматически переводит open/planned заявку в in_progress при запуске задания; блокирует только done/cancelled. Документ описывает независимые стадии, прежний запрос пользователя — запрет запуска при Open. Нужно привести сервер и клиент к одному явно зафиксированному правилу; одной блокировки кнопки недостаточно |
| P1 | Состав и финансы | В заявке редактируются request_finance_generation строки; в задании они заблокированы, а новые строки задания редактируются отдельно. Исторический текст «после переключения записей» не даёт пользователю следующего действия. Нужен единый рабочий сценарий: где планируется состав, где корректируются цены, как создаётся дополнительное задание |
| P1 | Новый выезд / существующий общий выезд | В задании есть создание нового выезда, но нет прямого выбора существующего. Для объединения требуется найти выезд и выбрать задания в нём. Нужен отдельный вход «Добавить в существующий выезд», с явно показанными клиентами и заданиями |
| P1 | Назначение людей | Заявка хранит инженеров, задание хранит команду/ведущего, выезд хранит команду поездки и отдельно факт присутствия; ещё есть владелец и куратор. Нужно объяснить назначения и проверить defaults, чтобы изменение одной команды не выглядело как изменение всех сущностей |
| P1 | Сохранение заявки при навигации | Заявка использует таймер автосохранения и офлайн-очередь, задание/выезд — ручное сохранение. Переключение новых/существующих заявок, ошибка сохранения и Browser Back требуют отдельного сквозного прогона: не считать их покрытыми защитой задания/выезда |
| P2 | Длинная карточка задания | План и результат повторяют строки; финансы и административные блоки конкурируют с исполнением. Навигация к разделам уменьшает поиск, но не заменяет отдельную композицию страницы инженера и куратора |
| P2 | Выезд: план, факт и карта | Есть отдельные вкладки экономики/истории, присутствие свёрнуто внутри плана и факта, кнопка проверки стоянок ведёт на карту. Проверить, понятно ли, что подтверждение присутствия не фиксирует количество выполненных работ |
| P2 | Исторические черновики | 8 закрытых заявок имеют draft-задания без подтверждённого факта; общий канбан заполнен историческими черновиками. Нужен фильтр/отдельный сценарий сверки, который не выдумывает выполнение |
| P2 | Read-only | В задании неактивные формы отображаются как отключённые поля; при длинном составе это визуально похоже на сломанную форму. Проверить предпочтение текстового представления для исполнителя |
| P2 | Даты, поиск, ошибки | ISO-даты в задании, разные поля поиска, серверные ошибки загрузки без общей формы восстановления. Проверить идентификацию нескольких заявок одного клиента и видимость следующего действия при пустом результате |
| P2 | История и комментарии | Собственная история каждой сущности сохранена; история ответственности имеет отдельный блок. Проверить, можно ли быстро восстановить причину перехода, автора, решение куратора и контекст общего выезда без чтения нескольких журналов |

## Проверенные и обязательные пользовательские потоки

1. Диспетчер: заявка → список имеющихся заданий → редактирование нужного задания либо создание дополнительного → сохранение состава/команды/периода → назначение.
2. Выездная работа: задание → новый или существующий общий выезд → выбор нескольких заданий → сохранение маршрута/команды → исполнение и проверка присутствия. Результат работ и материалов вводится в задании.
3. Депо/удалённая работа: назначение и результат задания без обязательного выезда.
4. Частичное выполнение: сохранить сделанное → перенести только остаток с причиной → новое задание; исходный факт и цены остаются в источнике.
5. Куратор: проверить результат → при остатке/активных выездах увидеть причину блокировки → подтвердить после устранения условий. Подтверждение поездки и работ — разные действия.
6. Переходы между карточками: сохранить/отказаться от ухода/явно сбросить правки → вернуться к исходному ID и фильтрам.
7. Владелец после делегирования: вмешательство с причиной и история, уведомление текущему куратору.
8. Историческая заявка: не трактовать закрытый статус как факт выполнения; при известном факте использовать отдельное основание.

Первые DOM-регрессии добавлены для прогресса, фильтров/исходных ссылок, защиты переходов, сохранения disabled-состояний, доступности переноса и блокировки закрытия при активном общем выезде. Эти проверки не заменяют проход пунктов 1–8 в живом браузере.

Для финальной проверки нужны диспетчер/инженер/куратор, desktop и узкий экран 390 px, одна заявка с двумя заданиями, один общий выезд с заданиями двух заявок, частичный результат/материал, перенос, отмена, офлайн и повторный вход. Производственные записи использовать только для чтения; действия выполнения — на синтетических QA-данных.
