# Карточка выезда: план, присутствие и проверка результата

Статус: конкретное решение для ревью. Первый локальный PR реализует основу карточки и сохранения; полный автоматический жизненный цикл и окончательное утверждение результата выделены в следующие PR. Production не изменён.

## Принятые бизнес-правила

1. Оплачивается присутствие инженеров на объекте, включая ожидание. Факт труда — длительность присутствия × состав команды, в человеко-часах.
2. Клиентская выручка определяется согласованными нормочасами и дорогой. Присутствие не увеличивает её автоматически.
3. Инженеры не вводят длительность. GPS предлагает интервалы, менеджер разбирает исключения и подтверждает результат.
4. Изменение плана не меняет исходные GPS-точки, посещения и уже известное присутствие. Исключение заявки из выезда не отменяет саму заявку.
5. Исходный, текущий план и факт существуют отдельно. Старым данным не приписывается неизвестная история.
6. Старт/финиш по кнопке — в целевой модели сигналы, а не разрешение собирать либо удалять факты.

## Одна карточка на весь жизненный цикл

Карточка открывается до начала, в пути, после возвращения и после подтверждения. Постоянная шапка: выезд, автомобиль, команда, статус и версия.

**План и факт**: текущие даты, состав будущей команды, заявки, маршрут, исключённые заявки, накопленные километры, присутствие и причины изменений. Проверка присутствия находится здесь же. Однозначные закрытые стоянки предлагаются к принятию; незавершённые и спорные можно оставить на последующую проверку.

**Экономика**: предварительный расчёт текущего плана и доступного факта. Неполный факт обозначается как partial. Плановое редактирование начатого выезда не заменяет существующий финансовый снимок: отдельный plan_econ_snapshot содержит прогноз.

**История**: время, причина, автор в данных и предыдущие версии плана/присутствия. UI выводит последние 100 событий; в базе история не обрезается этим лимитом.

## Точный сценарий отмены заявки Б

Исходно: депо → А → Б → В → депо. Посещение А уже состоялось; автомобиль едет к Б.

1. Менеджер снимает Б с текущего плана и пишет причину.
2. План сохраняется через trip_plan_save в одной транзакции с проверкой версии.
3. Связь Б удаляется только из текущего trip_jobs; её сведения сохраняются в trip_job_history.
4. trip_stays и vehicle_positions не удаляются. Детектор учитывает историческую связь для посещений, начавшихся до исключения.
5. По кнопке рассчитывается оставшийся маршрут от свежей позиции автомобиля через ещё не посещённые точки. Это отдельный remaining_route, не замена уже проеханного трека.
6. Менеджер отдельно решает договорные последствия отмены; сохранение плана начатого выезда не переписывает финансовый результат.

Текущий PR не умеет автоматически определять повторное посещение того же объекта как новую задачу. Для такого случая маршрут нужно проверить вручную; модель повторных посещений требует отдельных visit_id.

## Модель данных первого PR

| Объект | Назначение |
| --- | --- |
| trips.workbench_revision | Оптимистическая блокировка карточки; изменяется также при старых путях изменения связей/присутствия |
| trips.plan_baseline | План на назначение/начало; для ранее начатых выездов — честно обозначенная версия при первом изменении |
| trips.plan_econ_snapshot | Прогноз изменённого плана отдельно от существующего финансового снимка |
| trips.remaining_route | Геометрия и километры остатка, опорная позиция и время расчёта |
| trip_revision_history | Предыдущие состояния с причиной и автором |
| trip_job_history | Исключённые связи и сведения о заявках; без каскадного удаления по job_id |
| trip_stays.crew_ids | Состав команды этого присутствия; последующая правка команды выезда его не заменяет |
| trip_stays.crew_source | snapshot / manager / legacy_unverified |

Существующий trip_jobs остаётся текущим планом, поэтому основные списки и планировщик сохраняют совместимость. Сохранение из карты больше не восстанавливает заявки автоматически по координатам клиента.

Для старых стоянок нет достоверного снимка команды. Миграция не умножает исторические часы на нынешнее количество людей. Менеджер подтверждает состав при проверке.

## Контракты RPC

- trip_workbench_read(trip): текущая карточка, стоянки, исключённые заявки, история. Только активный admin/logist.
- trip_plan_save(trip, expected, plan, jobs, reason, stays?): whitelist плановых полей, блокировка строки, проверка версии, дифференциальное обновление связей и основной заявки, возврат id. Если одновременно редактировалось присутствие, оно сохраняется в той же транзакции. Ошибка откатывает всю операцию. Передать fact_km, started_at или произвольное поле в plan нельзя.
- trip_presence_detect(trip, expected): обновляет предложенные стоянки; утверждённые интервалы и их состав не затирает. Незакрытая стоянка остаётся незакрытой до конца интервала/выезда.
- trip_presence_save(trip, expected, stays, reason): проверяет принадлежность записей, длительность и состав; пересечения одного инженера внутри выезда запрещены. Сохраняет старое присутствие в истории и применяет изменения одной транзакцией. Допускает частичную проверку; это не считается полным фактом.

Во всех новых RPC проверка роли закрыта при NULL и inactive. Новые таблицы имеют RLS и доступны клиенту только на чтение менеджерам. Служебные функции находятся в закрытой схеме dlight_private. Старые проблемы RLS/RPC из аудита этим PR целиком не исправляются.

## Экономика и сводка

- Человеко-часы включаются в расчёт только после проверки всех учитываемых стоянок выезда и исторического состава. Непривязанная/непроверенная стоянка означает неполное покрытие.
- Ноль — допустимый подтверждённый результат; null — отсутствие данных. Пустой ввод не должен превращаться в ноль.
- Полный fact требует и километры, и человеко-часы. Если есть что-то одно, это partial, а cost_fact остаётся null.
- Финансовая сводка сравнивает выручку, затраты и прибыль одного набора подтверждённых выездов. Старые снимки с автомобильными часами вместо человеко-часов не выдаются за новый подтверждённый факт.
- При пересчёте используются сохранённые ставки начатого выезда и сохраняются плечи маршрута.

Проверенное присутствие распределяется по фактическим датам и каждому участнику, включая переход через полночь и летнее время. Планирование загрузки команды и сопоставление с выполненным объёмом требуют следующего PR; текущий коэффициент нельзя автоматически использовать для персональных премий.

## Целевой автоматический жизненный цикл — следующий PR

| Событие | Действие системы | Что делает кнопка инженера |
| --- | --- | --- |
| Подходит время назначенного выезда | Подготовить ограниченный буфер телеметрии автомобиля | Не нужна |
| Устойчивый выход из депо | Связать движение с единственным подходящим выездом; перенести буфер начиная с фактического выхода | Записывает подтверждающий сигнал, не заменяет время движения |
| Несколько подходящих выездов | Сохранить неразобранную сессию, поставить вопрос менеджеру | Может предложить привязку |
| Стоянка у объекта | Предложить посещение и человеко-часы по составу на интервале | Ввод минут не требуется |
| Возврат в депо | Создать кандидата на завершение с временем фактического прибытия | Дополнительный сигнал |
| Повторный выход в период ожидания | Продолжить тот же выезд | Не нужна |
| Устойчивое завершение | Закрыть оперативный выезд, подготовить проверку | Не нужна |
| Пропала телеметрия | Отметить пробел, не делать вывод о завершении | Не нужна |

Нужны отдельные параметры радиуса конкретного депо, гистерезиса, устойчивости выхода, подтверждения возвращения и максимального разрыва сообщений. Текущие 5 км / 60 минут нельзя автоматически считать подходящими для каждого депо: параметры должны пройти проверку по реальным обезличенным последовательностям телеметрии.

Согласованный факт сохраняется независимо от нажатий. Для неразобранных сессий задаётся отдельный ограниченный срок хранения; удаление назначенного выезда не должно быть побочным эффектом отсутствия кнопки. Текущие фоновые сборщики и сроки хранения первым PR не изменяются.

## Окончательное утверждение и корректировки — следующий PR

Единая серверная операция должна фиксировать принятую ревизию километров, присутствия, выполненного объёма, ставок, экономики и поправки одометра. Повторный запрос идемпотентен. Изменение подтверждённого результата создаёт новую ревизию с причиной; исходные GPS-точки не переписываются.

Существующий trip_confirm пока не заменён. Корректировка начала/конца, ручное добавление отсутствующих посещений, разрез интервала при смене команды и согласованная поправка одометра требуют этого следующего этапа. Подтверждение текущей карточки не следует путать с уже выполненной реализацией всех этих контрактов.

## Приёмка и развёртывание

Сначала закрыть P0 A01/A02 аудита отдельным изменением. Затем на staging-копии проверить миграцию вместе с реальными триггерами, RLS, удалением через корзину, GPS-детектором и обоими путями сохранения. Локальный PGlite проверяет SQL и транзакции на минимальном контракте схемы, но не заменяет staging.

Развёртывание: миграция → обновлённый frontend → проверка под admin/logist/engineer/inactive. Если RPC отсутствует, новая карточка блокирует сохранение; небезопасного fallback с DELETE+INSERT нет.

Откат UI возможен без удаления новых таблиц, но старый UI не понимает человеко-часы и версии. Полный откат должен быть заранее проверен на staging. Нельзя удалять историю или обнулять новые поля для удобства отката.
