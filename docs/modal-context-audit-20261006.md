# Окна и контекстные панели DLIGHT · аудит 06.10.2026

Проверяемый исходник: main `dbe9b49e390ced0fb40d60f943880108a8492f5a`, визуальный слой `src/visual-system.css`, сборка `83f4d22`. Это реестр и оценка, без изменения интерфейса, рабочих данных или правил подтверждения.

## Вывод трёх ролей

**Chief UX Designer.** Короткие сценарии обычно понятны: подтверждение, предложение правки, перенос, профиль, материал. Основная перегрузка — совмещение списка техники с полной формой её создания, открытые технические поля клиента и каталог работы с текстовым форматом материалов/мануалов. Сохранение и отмена длинных форм достижимы после прокрутки. Следует отделить основное действие от настройки, редкие поля раскрывать, важное состояние машины/подтверждения показывать явно. Не прятать ошибки и последствия действия в «?».

**Creative Designer Director.** Главная оболочка модалок уже близка к общей системе: радиус 16 px, поля и обычные кнопки 8 px, мобильный отступ 16 px. Однако старые подписи всё ещё Mono/uppercase, окна присутствия и выбора инженеров имеют собственные отступы 14/10 px, действия Leaflet имеют отдельные маленькие плашки. Самый заметный дефект — действие «Начать выезд» в попапе графика: подпись раскладывается почти по одной букве, кнопки вытягиваются до 183 px высотой. Нужно единое оформление трёх семейств: короткий диалог, форма, контекстная панель.

**Head of UI and Frontend.** Главные проблемы находятся в границах видимой карты и в поведении старых overlay. Меню слоёв, попапы и легенда не согласованы с нижней шторкой и друг с другом. Старые модалки не делают фон inert и не удерживают фокус; в подтверждении после последней кнопки Tab попадает на фоновый `undoBtn`. Native dialog профиля/присутствия удерживает интерактивный фокус внутри. Нужна общая оболочка с доступным названием, закрытием, возвратом фокуса и корректной высотой, с отдельными исключениями для обязательного входа и неподтверждённых изменений.

**Согласованное решение:** сначала доступность действий карты и попап графика; затем общая оболочка и сохранность ввода; затем формы техники/работ/тарифов; после этого типографика и мелкие отступы. Оценка не является автоматическим разрешением переписать финансовые значения, подтверждения присутствия или историю.

## Как составлен список

Обнаружено **44 активных семейства окон**: 21 статический overlay, два native dialog приложения, полноэкранный просмотр фото, девять контекстных панелей, девять семейств Leaflet-попапов и два вида системных окон браузера. Семейство считается один раз: один prompt обслуживает несколько бизнес-сценариев, один компонент «?» обслуживает все пояснения.

Дополнительно учтены три пассивные поверхности (toast, отмена, индикатор работы), inline-результаты геопоиска/коридора и неиспользуемый старый попап команды. Панели вкладок заявки, задания и выезда, раскрываемые карточки и обычные select/date-пикеры являются содержимым страниц или стандартными контролами, а не отдельными окнами приложения.

Прочитаны `docs/visual-system-20261004.md`, `docs/visual-qa.md`, CSS приложения и обработчики каждого семейства. Правила: шкала отступов 4/8/12/16/24/32; радиусы 8/12/16; Sans для текста, Mono для чисел; цели основных touch-действий от 44 px; читаемые переносы; ясное основное действие; техническое пояснение под «?», а текущее состояние/ошибка — видимо.

Браузерный стенд: Chromium, реальные шаблоны/стили текущего исходника, локальные шрифты/Leaflet, синтетические чтения. QA-only hooks позволяют открыть редкие сценарии без записи; hooks не входят в production. Внешние запросы блокируются, fixture writes отвергаются. Для карты перед открытием попапа дожидаемся показа и перерасчёта размеров; для выбора инженеров поле сначала прокручивается в видимую область. Это исключает ложные результаты от скрытой карты или программного клика по невидимому полю.

Размеры: 360×800, 390×844, 390×500 и 1440×900, светлая/тёмная темы. 390×500 — проверка ограниченной высоты, **не эмуляция настоящей экранной клавиатуры**. Измеряются границы, переносы кнопок, touch-цели, перекрытия центров элементов, прокрутка до последнего действия, Escape и переход Tab с последнего элемента. Для native dialog краткий переход фокуса на BODY/браузерную границу не считается выходом на фоновый интерактивный элемент: проверяется следующий Tab. PNG просмотрены отдельно от измерений. Нативные browser confirm/prompt оценены по исходнику и вызывающим сценариям: Chromium-снимок страницы не содержит системную поверхность браузера.

| Код | Приоритет | Подтверждение и решение |

| W01 | P1 | «Слои» на 360×800: панель 493 px высотой начинается на y=56; её нижние контролы накрывает шторка карты. На 390×500 низ y=549 уже за экраном. Нет внутреннего ограничения высоты/прокрутки. | W02 | P1 | Leaflet учитывает размеры карты, но не занятую нижней шторкой область. После стабилизации карты кнопки клиента/депо/техники всё равно перекрыты. | W03 | P1 | В попапе графика четыре действия делят узкий ряд: на 360 px высота ряда 183 px, «Начать выезд» читается вертикально по буквам. Вынести главное действие отдельной строкой; остальные — сетка с минимальной шириной или список. Геометрическое «текст не вылез за кнопку» этого дефекта не ловит. |
| W04 | P1 | Большинство старых overlay не удерживают фокус и не имеют dialog semantics. В подтверждении удаления Tab уходит на фоновую кнопку отмены. Использовать общую оболочку/native dialog, inert фон, aria-labelledby, безопасный начальный фокус и возврат к вызвавшему действию. |

| W13 | P2 | Escape и возврат фокуса различаются между окнами. Основные кнопки многих старых окон рабочие, но общего договора нет. Вход — оправданное исключение; изменение формы требует безопасного закрытия, а не общего remove('on'). |
| W14 | P3 | «?» имеет круг 32 px на touch. Можно оставить визуальный круг, расширив hit area до 44 px и не увеличивая плотность строки. Engineer options используют 10 px padding; привести к шкале. |

P1 — мешает действию или нарушает базовое поведение окна. P2 — ухудшает чтение, ввод или сохранность формы. P3 — доведение общего языка и очистка наследия. Визуальные дефекты не означают потерю подтверждённых данных.

## Порядок последующей реализации

1. Общий мобильный safe rect карты: шторка, инструменты, легенда и попапы; адаптивный показ слоёв/факта. Проверить реальные tap-цели через elementFromPoint и снимки.
2. Исправить layout `.gpop`, не меняя координаты/drag геометрию расписания. Проверять читаемость слов и разумную высоту кнопки, а не только отсутствие overflow.
3. Общая оболочка коротких диалогов и форм: название, header/close, внутренний scroll, footer, inert/focus, Escape/фон, возврат, безопасное поведение dirty. Обязательный auth — отдельное исключение. Подпись — distinct abort.
4. Разделить список и форму техники; сгруппировать работу, тариф и клиента. Техническую справку переносить в «?», актуальные статусы/ошибки/единицы оставить видимыми.
5. Общие типографика/радиусы/отступы и touch targets; затем async замена browser prompts/guards и удаление подтверждённого неиспользуемого UI.

При реализации не менять подтверждённые стоянки/треки, финансовые ставки и доли, RLS/роли или логику offline replay ради визуального упрощения. Для изменения поведения сохранения отдельно нужны meaningful сценарии dirty/отмены/ошибки/повторного открытия.

## Воспроизводимость и границы

Скрипт: `tests/visual/audit-windows.mjs`. После `npm run build`:

```sh
node tests/visual/audit-windows.mjs
```

При необходимости указать `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`. Узкий запуск: `WINDOW_AUDIT_PROJECTS=mobile-360-light WINDOW_AUDIT_CASES=layersPop,gpop,account-profile node tests/visual/audit-windows.mjs`. Скрипт запускает локальный QA server сам. Результаты — `test-results/window-audit/measurements.json`, `summary.json`, PNG по проектам; они игнорируются Git. Успешный рендер не означает отсутствие замечаний: это аудит, а не тест с искусственным зелёным вердиктом.

Итог: 46 сценариев представления × восемь сочетаний размера/темы, с двумя предусмотренными исключениями шторки «Ещё» на ПК: **366 попыток, 364 отрисованных состояния, два воспроизводимых отказа открытия выбора инженеров на 390 px, ноль fixture writes и pageerror**. Два отказа перепроверены отдельно и повторились, не записаны как успех. Дополнительные два измерения тёмной темы подтвердили низкий контраст danger-кнопок. Снимки просмотрены для всех типов обычных модалок и контекстных панелей на мобильном, отдельно в тёмной теме/короткой области и для спорных попапов/ПК. `node --check` и `git diff --check` прошли. Runtime-исходники приложения и миграции не изменены.

Ограничения: Chromium, синтетический backend, без записи; нет реальной авторизации, подписки push, внешнего геокодера/тайлов, физического телефона, Safari/Firefox, настоящей клавиатуры, сотен сотрудников/стоянок и полного проигрывания вложенных операций. Эти ограничения не мешают подтвердить геометрию, плотность и несогласованное поведение видимых оболочек.
