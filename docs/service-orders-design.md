# Заявка → сервисное задание → выезд

Согласовано: заявка описывает потребность, задание организует выполнение, выезд хранит транспортный факт. Задание объединяет несколько заявок; заявка участвует в нескольких заданиях. Выезд имеет ровно одно родительское задание. Канбан сохраняется, мобильный список и выбор статуса остаются альтернативой перетаскиванию.

## Первая поставка модели

`service_orders` хранит команду, ответственного, период, инструкции, место выполнения и отдельный статус. `service_order_jobs` хранит связи с заявками и исходный снимок. `service_order_items` хранит конкретный порученный объём и результат, с устойчивым ID; `source_item_id` и `transferred_qty` обеспечивают перенос остатка без повторного зачёта. `service_order_history` хранит автора, событие и прежнее состояние. `trips.service_order_id` задаёт родителя поездки.

Существующие `job_works` пересоздаются некоторыми путями сохранения. Поэтому строки поручений не ссылаются на нестабильные ID. Диспетчер задаёт конкретный объём и единицу; единицы разных строк не суммируются в общий процент. Автоматическое распределение всей потребности и закрытие заявки по этим строкам не выполняется.

Поездки переносятся с исходными связями и снимком. Для них создаются черновики заданий: окончание поездки не доказывает выполнение работ. Исторические объёмы не выдумываются. Существующие треки, стоянки и результаты проверки не изменяются. Старые пути создания поездки получают родителя через совместимый триггер. Новая поездка создаётся из задания атомарно; заявки поездки должны входить в задание.

## Статусы

Черновик → назначено → в работе → на проверке → завершено.
Из работы возможна приостановка с причиной; после проверки возможен возврат в работу. Отмена с причиной доступна диспетчеру до проверки, но не при активной поездке. Назначение требует команды, ответственного, периода и работ. Подтверждение требует выполнения или передачи всего остатка. Завершение задания не меняет статусы заявки и поездки.

## Дизайн-контракт

Режим Operate. Сохраняются существующие токены DLIGHT, канбан, жёлтый акцент действия, компактные поля и плавающий выбор команды. Новая декоративная оболочка не вводится.

Порядок: контекст заявки → название/состояние задания → сохранение → порученные работы и организация → результат → транспорт → история. Дочерние задания раскрываются внутри карточки заявки; общее задание представлено одним ID под каждой исходной заявкой. Отфильтрованный канбан даёт обзор заданий конкретной заявки.

Desktop: канбан со скроллом в доступной высоте; карточка задания в двух колонках. Mobile: один список по сроку, одна колонка редактора, изменение статуса без drag-and-drop. Имена/содержание экранируются. Ошибки остаются рядом с сохранением; введённое не сбрасывается при конфликте ревизии. Уход с изменениями требует явного решения.

Обязательные состояния: загрузка, ошибка с повтором, пустая доска, фильтр без совпадений, черновик без команды, перенос исторического выезда без состава работ, частичное выполнение, переданный остаток, конфликт версии, чужое/неактивное назначение, работа без поездки.

## Границы совместимости

Эта поставка добавляет устойчивый слой выполнения и навигацию. Старые финансовые расчёты, материалы, фотографии, подписи, присутствие и график ещё используют существующие таблицы заявок/поездок. Их нельзя просто скопировать в задания: это удвоит учёт. Для следующего переноса нужны устойчивые записи фактических работ, посещений и распределение затрат с единственным источником истины. Старый обзор поездок доступен для проверки накопленной истории.

Миграция аддитивна. Права на новые таблицы — только чтение с RLS; записи через операции с проверкой пользователя, роли, состава и ревизии. Инженер видит только свои задания и не подтверждает их результат. Менеджерские операции не доверяют входным полям статуса/автора.
