# Валидация трека и восстановление присутствия

Стандартная операция `rebuildTripTrack` объединяет прежнюю валидацию пробега и предложения присутствия. Её вызывают проверка/достройка в выезде и сведение факт-пробега. Просмотр карты не делает записей.

ORS-ответы кешируются внутри операции, бюджет запросов общий. Длительность маршрута сохраняется отдельно от разницы GPS-времён. Для пропущенного прибытия, отъезда и полного островка формируются интервалы предложения. Полный островок строится через единственный достижимый объект; несколько возможных объектов, отсутствие соседних подтверждающих точек, недоступный ORS и отрицательный остаток остаются неразрешёнными.

Достоверная GPS-часть складывается из соседних наблюдаемых точек в зоне объекта с интервалом до пяти минут. Долгое молчание между одинаковыми координатами не становится GPS-фактом. Синтетические старт/финиш не служат временными опорами для присутствия.

`trip_track_rebuild_context` выдаёт версию выезда, список объектов, временную границу GPS и digest. Чтение ограничивается этой границей, поэтому новая текущая точка не обрывает длительный расчёт; изменения/догрузка более ранних сообщений обнаруживаются при сохранении. `trip_track_rebuild_save` атомарно сохраняет разбор, предложения и при необходимости факт-пробег. Полномочия — существующий менеджер/владелец/куратор выезда. Anonymous и обычный инженер не записывают результат.

`presence_evidence` хранит наблюдаемые интервалы и достройки. `recovery_acceptance` хранит принятые менеджером минуты каждой достройки. Подтверждение идёт через прежний `trip_presence_save_tasks`, включая назначение долей заданий в той же транзакции. Сервер проверяет GPS-границы по реальным сообщениям, запрет подмены доказательств, диапазоны частей, принадлежность объектов, пересечения и версию. GPS-часть нельзя сократить. При 180 мин GPS + 180 мин достройки итог — 180…360 мин. Наследованные записи без новой evidence продолжают использовать прежний контракт; массового backfill нет.

Для начала принимаются последние выбранные минуты перед наблюдаемой частью; для конца — первые после неё; для полного островка — первые минуты внутри предложенного интервала. Наблюдаемые интервалы сохраняются целиком. Время внутри нескольких частей редактируется отдельно. Аналитика раскладывает принятые интервалы по датам, без размазывания часов по провалам.

Повтор идентичного расчёта не сбрасывает подтверждение и не добавляет часы. Обновление ORS сохраняет решение менеджера, если GPS-часть и принятые временные интервалы остались теми же. Остальные изменения evidence возвращают стоянку на проверку и сохраняют прежнюю запись в истории. Повторная достройка не может вырезать GPS-интервал, который всё ещё подтверждается исходными сообщениями. Устаревшее предложение без GPS снимается; архивная наблюдаемая/наследованная запись не удаляется. Пересчёт по неполному после retention исходному треку не заменяет ранее сохранённый разбор.

В интерфейсе отдельно показываются общая календарная продолжительность выезда, дорога (расчётная часть подписана) и подтверждённые стоянки. Остаток остаётся неразнесённым до решения менеджера. Нормочасы выполнения задания не изменяются, предложения не входят в подтверждённые человеко-часы и себестоимость.

Миграция создана Supabase CLI: `20261012135646_trip_track_presence_recovery.sql`. Прежний sparse-message детектор не перезаписывает проверенную evidence и не создаёт стоянки из провалов после перехода выезда на общий расчёт.

Дополнение `20261012144614_trip_presence_recovery_refresh.sql` сохраняет применимые решения менеджера при обновлении ETA и защищает наблюдаемые интервалы при повторном расчёте. Обе миграции проверены на PGlite, в том числе вызовами с реальными ролями Postgres. Браузерный сценарий использует готовую сборку приложения и синтетический backend; настоящие RPC дополнительно проверяются SQL-тестами.
