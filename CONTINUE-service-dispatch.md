## Что уже согласовано с пользователем

1. **Три главные сущности**: заявка `jobs` описывает клиента, потребность, технику, место и SLA; задание `service_orders` описывает исполнение одной заявки; выезд `trips` хранит исключительно выездные данные (маршрут, трек, стоянки, пробег, поездочные расходы). У одной заявки может быть несколько заданий. Одно задание относится ровно к одной заявке. Один выезд может объединять несколько заданий, в том числе из разных заявок; одно задание может участвовать в нескольких выездах.
2. Канбан заявок сохраняется. Дочерние задания доступны из заявки, задания имеют диспетчерский обзор/канбан; общий выезд показывается по одному ID в каждом связанном задании.
3. **Разовый исторический перенос:** для каждой уже существующей заявки с выездом создать **одно базовое задание на `job_id`**, а не задание на каждый выезд. Все её старые выезды привязать к этому заданию. Общий выезд привязать к базовому заданию каждой включённой заявки. Старые подтверждённые стоянки с `job_id` разрешено отнести к базовому заданию той же заявки, сохранив исходные ID, время, людей, подтверждение и часы. Это разовое заполнение, не правило для вновь создаваемых заданий. Повторный запуск переноса не создаёт дублей.
4. У каждой сущности собственный статус и история. Целевые стадии: черновик → запланировано → в работе → на проверке → закрыто; отменено — отдельный исход. Изменение дочернего статуса не меняет автоматически родительский. Показатель прогресса дочерних сущностей вычисляется отдельно.
5. Владелец, куратор и исполнители; исполнитель предлагает переносы/правки, куратор утверждает. Нужна оргструктура сотрудников и руководителей для контролируемой передачи владения. Задание хранит построчные материалы со снимком цены и себестоимости; во вкладке каталога нужен «Склад». Не вводи фиктивные остатки склада из старых затрат.
6. Выручка и себестоимость — разные распределения. Распределение транспортной выручки по плательщикам уже есть. Для транспортной себестоимости согласовано направление: фактический трек разбивается на участки по остановкам, затрата относится к заданиям соответствующей точки; нераспределённые участки остаются видимыми. Конкретные исключения и суточные/ночлег требуют отдельной реализации и проверки.

Обнови чтение, запись, подсказки, канбан и экран задания вместе с серверным контрактом. `src/app.js` и `src/trip-workbench.js` по-прежнему используют `trip_jobs` и `trip_stays` для маршрута, факта и UI. ## Порядок работы

### 1. Инвентаризация, доступ и обратимость

Проверь `git status`, ветку, GitHub, доступ к Supabase и историю применённых миграций. Читай схему и факты в режиме только чтения до изменений. Нельзя слепо запускать `supabase db push`: локальные временные метки миграций ранее отличались от производственной истории (см. `docs/telemetry-lifecycle-rollout.md`). Используй навыки/инструменты Supabase, доступные в среде; не выводи секреты в журнал и не записывай их в репозиторий.

Собери перед переносом хотя бы эти числа: число различных `trip_jobs.job_id`; заявок с несколькими выездами; выездов с несколькими заявками; стоянок по `job_id`, в том числе утверждённых; стоянок без `job_id`; выездов без `trip_jobs`; заданий с нулём/одной/несколькими `service_order_jobs`, заданий с результатом и связанных строк `service_order_items`. Разделяй активные и мягко удалённые поездки. Сними проверяемые агрегаты часов и финансов; не копируй в отчёт персональные координаты или секреты. Сохрани способ отката/точного отключения новой логики до переключения клиентов.

### 2. Аддитивная схема и идемпотентный перенос

В новой миграции добавь `service_orders.job_id` (пока nullable для старых данных), отдельную связь выезда с заданием, например `trip_service_orders(trip_id, order_id)`, необходимые индексы, внешние ключи, RLS и контролируемые операции. Не удаляй в этой же фазе `service_order_jobs`, `trip_jobs`, `trips.service_order_id`. Для канонического нового задания сервер должен проверять один `job_id`, а для включения в выезд — допустимый статус и режим. Проверки должны быть на стороне БД, не только в интерфейсе.

Разовое правило переноса — **одно базовое задание на один distinct `trip_jobs.job_id`**. Записывай происхождение и уникальный признак/карту переноса, чтобы операция была повторяемой без дубликатов. Если заявку уже обслуживает осмысленное вручную созданное задание, не сливай его молча с импортным: инвентаризируй такие случаи и принимай решение по конкретным данным. Старые заказы, автоматически созданные по поездкам, после переноса не должны выглядеть в канбане как дополнительный активный набор заданий. Пока `trips.service_order_id` обязателен, сохранённый старый родитель может оставаться технической опорой; не удаляй его и историю, пока каждый потребитель не переключён.

Создай связку `trip_service_orders` для каждой пары `trip_jobs.trip_id/job_id` через карту базовых заданий. Уникальность пары защищает повторный запуск. Стоянку с `job_id`, однозначно разрешённым этой картой и участием в выезде, привяжи к заданию (ссылкой либо отдельной строкой происхождения), **без вставки второй стоянки**. Неоднозначные или отсутствующие связи покажи в журнале исключений. Значения `minutes_mgr`, `crew_ids`, `status` не меняй. У старых `service_order_items` используй `job_id` для переноса к соответствующей заявке, сохраняя `done_qty`, `transferred_qty`, `source_item_id` и историю происхождения; проверь внешние ключи и цепочки переноса остатка. Общие поля старого задания (команда, даты, статус) нельзя бездумно копировать в базовое задание, которое объединяет несколько поездок. Завершённый выезд не доказывает завершение работы: безопасное исходное состояние базового задания — черновик/требует уточнения, если нет другого подтверждённого результата.

### 3. Параллельные пути записи и переключение интерфейса

Особенно внимательно перепиши логику `trip_order_parent`, `trip_order_job`, `service_order_trip` и другие записи `trip_jobs`. Сейчас триггер при добавлении заявки в поездку добавляет её в старое родительское задание, а это вновь создаст многозаявочное задание. Новые операции должны добавлять задания в **связку выезда с заданиями**. Старый редактор выезда на переходе обязан либо атомарно создавать недостающее базовое задание для новой заявки, либо явно передавать управление новому потоку; он не должен оставлять выезд с неполным набором связей. Обновляй серверные функции и клиентов согласованно, проверяя конкурирующие сохранения и ревизии.

Измени `src/service-orders.js`: один выбор заявки при создании задания, список связанных выездов по новой связке, дочерние карточки в заявке, фильтр канбана. В редакторе выезда можно выбрать несколько заданий из разных заявок и увидеть, какой заявке принадлежит каждое. Прямой `trip_jobs` на переходе сохраняется для нынешней логики маршрута/стоянок; синхронизация должна иметь один определённый источник истины, транзакционную запись и отсутствие рекурсивных триггеров. Протестируй создание заявки → задания → общего выезда, редактирование состава, сохранение стоянки и отмену/удаление.

Сохрани сделанные ранее требования UI: компактные карточки и кнопки, раскрывающийся в один ряд выбор инженеров поверх карточки без изменения размера карты, доступная горизонтальная прокрутка канбана и на мобильном альтернатива drag-and-drop. При конкретных UI-изменениях используй установленный навык Uizze anti-ui-slop и визуальный предпросмотр; не помещай секреты Uizze в код.

### 4. Учёт, роли и каталог — отдельные проверяемые порции

После корректной структуры свяжи новый факт стоянок с заданием: новая стоянка может относиться к нескольким заданиям на одной точке и требует явных долей человеко-часов. Старые стоянки наследуют базовую связь по согласованной разовой карте, и только её; при новом разделении заявки на несколько заданий старую историю не перераспределяй молча. Для километров испытывай участки реального GPS-трека; неопределённые участки и разницу с одометром держи явным остатком. Проверь инвариант по компонентам: распределённое на задания + не распределено = подтверждённый итог выезда, включая отдельную строку ручной корректировки. Не добавляй транспортную себестоимость поверх целого `econ_snapshot.cost`.

Оргструктуру вводи поверх существующих `profiles.id`, чтобы не сломать RLS и назначения; отдельный кадровый ID нужен лишь при подтверждённой потребности учитывать сотрудников без аккаунтов. При передаче владельца руководитель должен быть активным и иметь необходимые права; иначе назначение ждёт куратора. Материалы задания хранят снимок значения; вкладка «Склад» сначала может быть справочником. Физические остатки, резервы и движение между складом и автомобилем требуют отдельных правил и начальной инвентаризации.

## Проверки и выпуск

- Дай интеграционные тесты миграции: одна заявка с 2+ выездами → одно базовое задание; выезд с 2+ заявками → столько связей с базовыми заданиями, сколько уникальных заявок; повторная миграция → те же IDs и количество; стоянка с `job_id` → ровно одна историческая запись и правильное задание; без `job_id` → исключение, а не фальшивая связь. Отдельно проверь существующие ручные задания, старые строки с `done_qty` и `source_item_id`, мягко удалённые выезды и RLS инженера/диспетчера.
- Проверяй полный пользовательский сценарий на предпросмотре (десктоп и узкий экран), особенно канбан, карточку задания, общий выезд и стоянки. Запусти `npm run lint`, `npm test`, `npm run test:tz`, `npm run build` и `node tests/smoke.cjs dist/index.html`. В CI `.github/workflows/deploy.yml` повторяет эти проверки. PGlite-тесты не заменяют проверку фактической схемы и RLS на Supabase.
- Перед продуктивной миграцией зафиксируй исходные агрегаты и зависимости, проверь историю версии на конкретном проекте `anqfbljgfimoaziztdxe`. Применяй только совместимую, проверенную миграцию; после неё проверь число связей, часов, итогов и работу старых экранов, затем переключай сайт. Если миграция или проверка не прошла, не запускай публикацию несовместимой сборки.
- GitHub Pages собирает `dist` из `main`. PR и обычный push выполняют сборку без публикации; деплой происходит после успешной сборки по `workflow_dispatch` на `main` либо при `[deploy]` в сообщении push-коммита. После слияния и публикации проверь успешный workflow, загрузку действующего сайта, штамп сборки из `vite.config.js` и основные сценарии с доступной ролью. Разрешение на PR/merge/deploy есть, повторно спрашивать его не нужно.
